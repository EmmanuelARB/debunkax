# A Listening Session can hear from the microphone or from the device's app audio

A session always heard from the room through the microphone. The user then wanted to fact-check what is played on the tablet itself (a YouTube video, France.tv Pluzz), where the mic path only works with speakers on and a quiet room. Android allows an app to capture another app's audio output — the `AudioPlaybackCapture` API, which is exactly the "live captioning" use case it was built for — so the start button now asks which source: **Microphone** (the room, the default) or **Audio des apps** (this device's media playback only). Both sources are the same 16 kHz mono stream, so nothing downstream changes: speech-to-text, the Claim filter, speaker recognition and the Check all work identically. We rejected MediaProjection screen recording with audio (the same consent, but it also captures the screen and signals something the app does not do) and any form of passive always-on capture, which does not exist on Android anyway.

## Consequences

- App-audio sessions run through the same per-session consent the platform mandates: a system "start recording" dialog, a foreground service of type `mediaProjection` (mandatory since Android 14) with its notification, and a red recording icon — all of which the user can revoke at any time from Quick Settings. When the token is revoked, the audio source ends and the Listening Session stops itself, closing its History row (which also fixes the same latent leak in the scripted demo mode).
- App-audio sessions are the one exception to "listening only in the foreground" (AGENTS.md, amended by this ADR): they keep running while the app is in the background, because that is the use case — the video plays in another app. Mic sessions still stop as soon as the app leaves the foreground. The platform's consent, persistent indicators and revocable token are the control for the background case.
- Only media playback is capturable, and we capture only `USAGE_MEDIA`: ringtones, notifications and calls are out of scope by the platform's design. Apps may opt out of being captured; in practice the usual media apps (YouTube, France.tv Pluzz) are capturable — verified on the user's tablet.
- The capture is bound to a `MediaProjection` consent token via `AudioPlaybackCaptureConfiguration.Builder(projection)` (available since API 29, so minSdk 31 is fine); three platform constraints are non-obvious and cost real debugging: the foreground service must already be running when the token is requested, `setAudioSource` must not be called together with a capture config, and the config must carry at least one matching rule.
- The History and Alerts are unaffected: a Claim does not know where its audio came from.
- The privacy rules of AGENTS.md hold unchanged: listening is foreground-only and user-started, nothing is persisted, and the Check is the only thing that leaves the phone.
